# Classifier-Removal Review

Question: should classification leave Pass 1, given the decision that it must
serve post-ingestion consumers (wiki graph now, chat later)? And what can removal break?

**Verdict: remove, in this order — (1) build the standalone classifier beside the
pipeline, (2) point kwg at its output, (3) only then strip Pass 1.** Remove-first
creates a window where no new ingestion run can become a graph.

## Review 1: kip-consumers

Confirmed from the mechanical side, with conditions: inside kip the kt-v1 classification fields
are write-only — no pass branches on them and no prompt even renders them (all five prompt
contexts show the legacy unit_type label, and the fix there is deleting one f-string line each)
— and content_sha256 provably excludes the whole block, with migrate.py standing as working
proof that a post-ingestion classifier can stamp these fields onto finished runs without
breaking hash validation. So removal from Pass 1 is architecturally clean. But it is a
coordinated edit, not a deletion: the schema `required` array and REQUIRED_RAW_UNIT_FIELDS must
move together (else every unit is silently rejected and validate still exits 0 on an empty
corpus), eight bracket-access sites across route/assess/audit/extract/trace crash on KeyError
otherwise, DERIVED_FIELDS must keep the field names or every existing run fails hash validation,
entity_mentions must stay in Pass 1 because it needs the document and line numbers (it is
extraction, not classification), and taxonomy.py stays as the shared kwg vocabulary. Two
accepted losses to flag to Anatoly: the type-tests section currently doubles as the prompt's
unit-splitting nudge (multi_fire split signal moves post-hoc), and validate's taxonomy health
metrics (40% unflagged-claim alarm, unclassified/multi-fire counts) silently disappear rather
than erroring — both need a home in the post-ingestion classifier. Demo, ~10 integration tests,
test_taxonomy.py, and the docs all assert the current shape and fail loudly, which is tedious
but safe.

## Review 2: kwg-consumers

Removing classification fields from kip's extraction pass hard-breaks kwg at load time with a
clean, named error (exit 2, no traceback) — kwg cannot build any graph until something re-
supplies the fields — but the code structure makes the fix the user already wants cheap: a live
probe proved that a separate post-ingestion step that annotates 02_units/units.jsonl in place
(same field names, taxonomy_version stamped exactly "kt-v1") makes kwg build byte-identically to
today with zero kwg changes, because kip's content hash already excludes every classification
field and kwg never re-verifies unit hashes. Classification inside kwg's build is the expensive
option: it contradicts kwg's stated contract ("inherits types and never re-classifies"), would
add a second LLM stage to a plugin whose cost/resume machinery assumes entity adjudication is
the only model call, and would strand the chat-statement use-case inside a document-graph
builder. Two traps need handling if removal ships: (1) three of the stripped fields (node_kind,
entity_mentions, flags) fail SILENTLY, not loudly — exit 0 with the question node demoted to an
assertion, all entities and mention edges gone, and hedge/lint metrics degraded — and
entity_mentions/node_kind are arguably extraction judgments, not classification, so they should
either stay in Pass 1 or the new step needs the normalized source text, not just statements; (2)
the load error's printed remedy (`kip migrate-taxonomy`) "succeeds" on a stripped run but yields
a 100%-unclassified graph, so that message must be rewritten to point at the new classification
step.

## Review 3: prompt-effects

none of the five downstream prompts defines or instructs on the type vocabulary — the labels are
bare inline tokens of the LEGACY 20-value unit_type (produced from an uninstructed schema enum,

is prior rather than observation; before committing, gate the five render sites behind a flag

scenario is precisely the case where label removal would show up, artifact diffing is trivial
because content_sha256 already excludes every classification field, and if the null/caveat
signal does prove to matter, rendering the two flags at the assess/audit sites is a far smaller
thing to keep than classification itself.
