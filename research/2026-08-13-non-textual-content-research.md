# Non-textual content in document pipelines: what the field does

**Date:** 2026-08-13
**Method:** six independent research agents with web search, each area's claims then
attacked by a different agent instructed to refute them. 49 claims produced, **39
survived** refutation. The 10 that did not are not reproduced here.
**Question asked:** what is current industry best practice for capturing formulas,
tables and figures, for a pipeline whose core guarantee is that every claim cites
source text verified verbatim.

**Why this exists:** kip flattens every source to one `normalized.txt`. Measured on
five real documents, that destroys equations (a 1985 t-statistic became the literal
string `Tt = ARw,t/(st/ViN)`), fuses table cells (`Total segment
revenue$33,314 $26,881 $23,855`), and reduces charts to axis-tick noise. The table
case is the dangerous one: the year-to-column mapping survives only in the model's
prose reconstruction, so a misread table still passes verbatim verification.

Linked from: `src/kip/normalize.py` (Pass 0), `docs/SPECIFICATION.md` §8.

## Synthesis and recommendation

# kip: non-textual content — what the field does, and what to do

*Grounded in the repo as it stands: `src/kip/normalize.py` routes `.html` to a regex tag-stripper (`_normalize_html`, line ~186) and only `.pdf/.docx/.pptx/.xlsx/.epub/.msg` to Docling. The GE 10-K table defect is **kip's own regex**, not a parser limitation — `re.sub(r"(?i)</(p|div|li|tr|h[1-6])>", "\n", raw)` breaks on `</tr>` but not `</td>`, so cells concatenate. That matters for the build order below.*

## 1. THE PRACTICE

### 1a. Tables — the field solved *addressing*, not *correctness*

**What everyone ships.** Every production document API returns a typed grid, not a string. AWS Textract `CELL` blocks carry `RowIndex`/`ColumnIndex`/`RowSpan`/`ColumnSpan` (1-based) plus `EntityTypes` including `COLUMN_HEADER`, `TABLE_TITLE`, `TABLE_FOOTER`. Azure AI Document Intelligence v4.0 (GA API 2024-11-30) returns cells with `rowIndex`/`columnIndex`/`rowSpan`/`columnSpan`, `boundingRegions`, a `kind` enum of `columnHeader | rowHeader | stubHead | content | description`, **and a `span` (offset+length) into a single top-level `content` string**. Docling's `TableCell` carries `start_row_offset_idx`/`end_row_offset_idx` (+ column equivalents) and `column_header`/`row_header`/`row_section` flags.

Note the correction to a common belief: Azure and Docling both give first-class **row** headers. Textract is the outlier that doesn't.

**The number that matters.** Structure recovery is not near-solved outside the academic benchmarks. TFLOP reports 99.45 TEDS on FinTabNet; granite-docling-258M reports 0.97 TEDS-struct. But on heterogeneous real documents (arXiv 2511.16134, Nov 2025, ~86k pages) Docling's structure score falls from **0.86 F1^TEDS on PubTables to 0.67 on arXiv preprints** — while its table *detection* barely moves (0.99 → 0.89). Detection generalizes; structure does not. Microsoft's TATR, still the reference open model, scores GriTS_Con 0.985 and **whole-table exactness (Acc_Con) 0.8243 on its own in-domain test set** — near-perfect on the averaged metric, 18% of tables not exactly right.

**The contested part, and it's the important one.** The field's default metrics are blind to exactly kip's defect. "Beyond String Matching" (arXiv 2603.18652, Mar 2026 — 21 parsers, 451 tables, human study of 1,554 ratings, α=0.77) measured correlation with human judgment of "can every cell value be unambiguously mapped to its row and column headers": **TEDS r=0.684, GriTS-Avg r=0.698**, versus LLM-as-judge r=0.927–0.939. It documents a parser turning `1.12` into `112` at negligible edit-distance cost. Caveat both ways: that corpus is 100 *synthetic* LaTeX-rendered pages, and the LLM-judge fix is circular for a pipeline that's auditing LLM output.

Header hierarchy specifically is near coin-flip. CHiTab (arXiv 2511.08298, Nov 2025) asked mid-size VLMs which sub-columns sit under a spanning heading: Granite Vision 3.2 40.9%, Qwen2.5-VL-7B 43.7%, Gemma3-27B 48.5%, Mistral Small 3.1 49.4%; 29 humans scored 63.2%. That's on a deliberately hard subset (~2.5% of PubTables-1M survived the filter) and no frontier model was tested — but it is the closest published measurement of "`SEGMENT REVENUE AND PROFIT / 2025 2024 2023`."

**Who's winning.** Not frontier VLMs. On OmniDocBench v1.6, MinerU2.5-Pro (1.2B) scores Table TEDS 93.42 against Qwen3-VL-235B at 83.07. Small document-specialist VLMs emitting structured markup (DocTags/OTSL/HTML) beat both DETR models and 235B generalists. Discount heavily: OmniDocBench is built by OpenDataLab, who also build MinerU. Every table benchmark naming a winner was published by the winner (Unstructured's SCORE-Bench → Unstructured; Reducto's RD-TableBench → Reducto; LlamaIndex's comparison → LlamaParse, with no dataset, sample size, or scores published at all).

### 1b. Formulas — string verification is actively misleading

**Nobody verifies formulas by string comparison, and the reason is measured.** UniMERNet scores ExpRate (exact string match) **0.4799** but ExpRate@CDM (visually identical after rendering) **0.8110** on the same test set — ~33% of outputs are visually perfect and textually different (Wang et al., arXiv:2409.03643, CVPR 2025). Rewriting 50 formulas five ways with GPT-4 left CDM constant at 1.0 while BLEU scattered. On the screen-capture subset the ranking *reverses* between BLEU and CDM.

CDM is not an oracle either. Horn & Keuper (arXiv:2512.09874, ICPR 2026; 250 formula pairs, 30 evaluators, 750 ratings) measured Pearson r against human ratings: **LLM-as-judge 0.78, CDM 0.34, BLEU/Levenshtein ≈0**. CDM false-negatives when a model emits Unicode instead of LaTeX, and can't score at all when the prediction doesn't render. The safe reading is *string metrics are misleading*, not *CDM is truth*.

**Storage format is settled: LaTeX in, MathML out.** Azure returns `value` as LaTeX; Docling extracts LaTeX and only renders MathML on HTML export; LlamaParse emits `$$…$$`; Mathpix Markdown is LaTeX-based; UniMERNet, Nougat, texify/Surya, GOT-OCR2.0, MinerU, PP-FormulaNet all emit LaTeX. Essentially nothing captures to MathML.

**Two failure modes worth more than the benchmarks.** (i) Recognizers are built for single cropped expressions and are out-of-design on pages: UniMERNet holds 0.919 CDM at line level, 0.644 at paragraph, **0.009 at page level** on CSFormula (arXiv:2508.00311, Aug 2025). Detection/cropping is where accuracy goes. (ii) Representation mismatch: rule-based extractors (pypdf, pymupdf4llm) emit Unicode symbols exclusively; OmniDocBench added hybrid text/formula matching in v1.5 (2025-09-25) specifically because models emitting Unicode were being scored as errors. kip's `Tt = ARw,t/(st/ViN)` is a *related but distinct* thing — a rasterized 1985 glyph mapped to unrelated characters before any model saw it. That specific mechanism is my hypothesis about your data, not a published measurement.

**And the popular tool drops formulas by default.** Docling ships `do_formula_enrichment = False`; users report the placeholder left behind (`<!-- formula-not-decoded -->`) is not addressable back to a crop — GitHub Discussion #925 is still unanswered, with a contributor confirming there's no option to retrieve the image. Issue #1883 ("Formula extraction is tacky and inconsistent") is open. Azure ships formula extraction as a paid, off-by-default add-on, and its docs carry the line "The `confidence` score is hard-coded."

### 1c. Figures — the field has given up on reading them

**Detect-and-crop is mature; understanding is not.** PDFFigures 2.0 (2016, still the baseline) hits 94% precision at 90% recall on CS papers. Docling's Heron layout models (arXiv:2509.11720, Sept 2025; RT-DETR/D-FINE on ~150k documents) reach 78% mAP at 28ms/image and are Docling's default.

**But financial documents are the measured worst case, and the ceiling is human.** DocLayNet (KDD 2022) measured triple-annotator agreement as pairwise mAP@0.5:0.95. Caption class: **94–99% Science, 95–99% Law, 40–61% Finance**. Picture class: 82–86% Manuals, 56–59% Finance. Partly a class-definition problem — 10-Ks contain few conventional "Figure N" captions — which makes it *worse* for kip, not better: caption-regex association has nothing to grab.

**Chart reading is not production-viable at any price point.** ChartQA is saturated: Claude 3.5 Sonnet goes 90.50% → **55.81%** on ChartQAPro (arXiv:2504.05506, ACL Findings 2025), Qwen2-VL-7B 89.5% → 37.17%, human baseline 85.02%. On unanswerable questions — the case a citation pipeline most needs — GPT-4o 50.13%, Claude 47.98%, Gemini 2.0 Flash 63.14% (so: model-dependent, not universally coin-flip).

Chart-to-table is worse. On WB-ChartExtract (arXiv:2605.27298, 2026; 1,000 synthetic charts, ~7× ChartQA data density, no printed labels): Gemini 2.5 Pro 87.83 RMS_F1, Claude Opus 4.6 60.99, GPT-5.1 51.26, **TinyChart 28.61 — against its own 95.20 on ChartQA**. DePlot last at 23.06. Error decomposition: value errors 19–40%, *missing cells* 22–42%, so an extracted table can look complete and silently omit a series. On ExChart-Bench (CHI 2026, real charts without data labels) the best MAPE is 6.72% (Gemini 2.5 Flash), worst 16.01%.

The vendors agree. Docling shipped chart understanding 2026-02-03 (granite-vision-3.3-2b-chart2csv-preview, bar/pie/line only) and reports **60.1 on Chart2CSV** — the field leader, at 60 out of 100 on its own task — with its own blog naming low-resolution scans, stylized charts and crowded multi-series plots as failure cases. Reducto's Figures API returns `figure_type` and `alt_text` and declines to guess numbers.

**Prose descriptions don't dodge it.** ChartHal (arXiv:2509.17481, Sept 2025; 1,062 human-validated samples): GPT-5 34.46%, o4-mini 22.79%, with hallucination concentrated exactly on information absent from or contradicting the chart. Honest caveat: ChartHal is QA, not free-form captioning — nobody has published a per-sentence hallucination rate for "have a VLM describe this chart."

**There is no standard for citing a chart's content.** FinRAGBench-V (EMNLP 2025 Main) is the one benchmark that measures sub-page citation: GPT-4o English scores page-level precision 81.81 / recall 89.98 versus **block-level 44.66 / 54.17**. And when a model is asked to emit coordinates directly, attribution collapses — arXiv:2607.24651 (Jul 2026) measured evidence recall 0.3–8.1% with **82–97% "attribution hallucination"** across six open VLMs; switching to a verbatim-quote interface that a retriever then matches to a layout block reached 25.9–46.9%, and 51.3% after GRPO training. The emerging practice is: cite the *region*, never the reading.

## 2. THE RECOMMENDATION FOR KIP

### Adopt DoclingDocument as an input adapter. Do not adopt it as kip's evidence model.

**Adopt:** Docling is already a dependency in `normalize.py`. Keep it as the parser, extend it to HTML (currently only PDF/Office go through it), and mirror its *vocabulary* so the adapter stays thin — `self_ref` JSON-pointer ids, `prov` with page + bbox, `TableCell.start_row_offset_idx` / `column_header` / `row_header`, OTSL for table serialization. A future DocLang or DoclingDocument export should then be a serializer, not a rewrite.

**Do not adopt it as the stored model.** Three specific reasons, all verified against docling-core:

1. **`charspan` is item-local, not document-global.** Construction sites pass `charspan=(0, len(text_content))` — an offset into that item's own text. Docling therefore cannot give you the span↔cell-address bridge that keeps kip's existing verbatim verifier working. **Azure's model can**, because its spans are offsets into one top-level `content` string. Copy Azure's addressing semantics, not Docling's.
2. **`content_layer` does not mean what people think.** The enum is `BODY / FURNITURE / BACKGROUND / INVISIBLE / NOTES` — page role, nothing to do with provenance. Docling has no transcribed-vs-derived typing. Its picture-description base model sets `self.provenance = "not-implemented"` in shipping code today (`picture_description_base_model.py:53`); the local VLM paths override it with a model repo_id, which is *who generated it*, not *what kind of content it is*.
3. **kip needs an XBRL fact type Docling has no slot for.**

**The core design decision: char span AND asset id, not OR.** kip's framing of "cites either a character span OR an asset id" is a false choice, and the two largest cloud services prove it. Azure keeps one flat `content` string as the canonical citation surface and layers typed elements carrying `{offset, length}` spans into it — down to individual table cells. Google Document AI does the same with `layout.textAnchor.textSegments` into `document.text`, which it calls "the source of truth of the document's text," including per-cell.

For kip that means: **`normalized.txt` stays exactly as it is.** Pass 7's verbatim machinery keeps working on day one. You add a sidecar element index. An asset citation and a span citation become the same object viewed two ways.

**The bundle-on-disk layout is five-year-old prior art.** Adobe PDF Extract has shipped `structuredData.json` + `tables/` (CSV, XLSX, PNG) + `figures/` (PNG) with a per-element `filePaths` attribute since October 2021. Azure generates cropped figure images at `/analyzeResults/{id}/figures/{figureId}` when you pass `output=figures`. Copy Adobe's layout — it's the most conservative and most tested. Two borrowings: write tables as CSV alongside the structured grid so a human can inspect a citation without running kip; and **always store the crop**, because Docling's issue tracker (#1503, #2376, #2349) is a record of users whose asset references silently became placeholders. Make an unresolvable asset reference a hard pipeline error.

### Build these

- **Bundle manifest** with schema version, parser name + version, and — this is a real trap Azure documents explicitly — the **offset unit**. Python `str` indexes code points; JS indexes UTF-16 units; Azure defaults to grapheme clusters. Record which one, or your consumers will silently disagree.
- **Element index sidecar**: `{element_id, type, page, bbox, char_start, char_end, extraction_method, produced_by}` for every table, figure, formula and XBRL fact.
- **Table grid asset**: cells with `(row, col, row_span, col_span)`, header flags, per-cell text, **per-cell char span**, and a `grid_sha256`.
- **XBRL fact asset** for the GE 10-K (see below).
- **Formula/figure assets** carrying the crop unconditionally.
- **A trust-tier enum enforced at the evidence layer** — this is the thing nobody in the field has and it's your highest-value original work.

### Skip these

- Chart-to-data extraction of any kind.
- MathML as a storage format (derive it lazily if you ever need rendering).
- PDF/UA structure tags as a load-bearing path — arXiv:2410.03022 (Oct 2024, 20k PDFs, 2014–2023) found **under 3.2% meeting all six accessibility criteria and 74.9% meeting none**, declining since 2019. CHI 2025 remediation work (arXiv:2503.22216) measured baseline tagging scores around 39–42% even where tags exist. Treat as an opportunistic bonus, verified before use.
- Waiting for DocLang. The LF AI & Data working group launched 2026-06-09 (IBM, NVIDIA, Red Hat, ABBYY, HumanSignal); spec is at v0.6. Two months old. Don't block.
- SEC `companyfacts`/`frames` APIs and the DERA Financial Statement Data Sets. The EDGAR XBRL APIs aggregate only facts that use a non-custom taxonomy **and apply to the entire filing entity** — that second condition excludes dimensional/segment facts outright, which is precisely the GE segment-revenue table. Post-Dec-2024 FSDS is primary-statements-only. Parse the filed iXBRL instance with Arelle.

### The one XBRL move that is free accuracy

The GE 10-K's 2,863 `ix:nonFraction` facts are already bound to 701 `xbrli:context` definitions carrying period + entity + dimensional members, plus 14 units. **The year-to-column mapping kip lost is stated declaratively in `contextRef`.** Run Arelle, emit each fact as `{fact_id, concept, value, unit, context(period, entity, dimensions), decimals, scale, sign, char span where the tagged text appears}`.

Two calibrations:

- **Coverage is partial.** SEC Rule 405(d)(4)(i) Level-4 detail tagging covers the financial statements and their footnotes — not Item 1, 1A, 2, 5, or most of MD&A. Your own ratio argues for this: 2,863 facts across 1,573 `<tr>` is ~1.8 tagged numbers per row, while a three-year comparative row needs three. So iXBRL solves *some* of the 107 tables. You still need a table path for the rest.
- **Displayed text is not the value.** `@scale` is a power-of-ten multiplier, `@sign="-"` flips polarity independently of printed parentheses, `@format` applies a Transformation Rules Registry rule (XBRL International, "iXBRL Tagging Features", 3 Oct 2019 — worked example: "$12.34 million" with scale 6 → 12,340,000). **A verbatim check against the printed string passes while the extracted number is wrong by three orders of magnitude or by sign.** This is a defect in kip's *verification* model, not just extraction, and it's the same shape as the table defect.

What this does *not* buy: LLMs failing to *generate* XBRL tags (FinTagging's FinCL at 0.1889 accuracy) is a different task from *reading* tags a filer already submitted. Reading is parsing and is essentially exact. Don't oversell it — the honest claim is "the filer already answered the question, so don't ask a model."

## 3. THE CITATION ANSWER

### Universal rule: three fields on every asset, enforced at the evidence layer

Modeled on PROV-O without adopting RDF:

```
extraction_method: native-structured | native-text | ocr | structure-recovered | model-described
produced_by:       "arelle-2.38.17" | "docling-2.119.0" | "claude-opus-5@2026-08-13"
evidence_class:    verbatim | structural | derived
```

**The rule that does the work: a candidate's *primary* evidence may only be `verbatim` or `structural`. A `derived` asset can be supporting context and can never satisfy a citation.** Enforce it in `audit.py` as a deterministic check alongside the existing `citation_accuracy` and `provenance_integrity` checks. That single rule is what stops a VLM chart caption laundering itself into the audit trail, and it is more than the state of the art currently delivers — Docling has the field and ships it as a string.

### A table cell

```json
{"evidence_class":"structural","asset_id":"tbl-004",
 "cell":{"row":7,"col":3,"row_span":1,"col_span":1},
 "row_header_text":"Total segment revenue","col_header_text":"2025",
 "cell_text":"$33,314","cell_text_sha256":"...",
 "normalized_char_start":812340,"normalized_char_end":812347,
 "grid_sha256":"...","extraction_method":"native-structured",
 "xbrl_fact_id":"f-01842"}
```

Verification is three checks, all deterministic:

1. **Verbatim (unchanged machinery):** slice `normalized.txt[812340:812347]` and compare to `cell_text`.
2. **Structural:** the stored `row_header_text`/`col_header_text` must resolve to `(7,3)` in the stored grid. This is the check that closes your dangerous defect — a misread table can no longer produce a self-consistent passing citation, because the label and the index are two independent stored facts that must agree.
3. **Value (iXBRL only):** `transform(cell_text, @format, @scale, @sign) == fact.value`.

Be honest about what index-addressing does and doesn't buy. If the parser merges two columns, cell (7,3) points confidently at the wrong number and verifies fine — the index alone is exactly as self-consistent as the header string. **What makes it safe is the per-cell char span back into `normalized.txt` plus the `grid_sha256`.** Cite the index *and* the anchor, or you've bought nothing. `grid_sha256` also catches the re-parse case: a parser upgrade that shifts indices (Docling #3698 reports multi-level headers shifting a row) becomes a detected mismatch instead of a silent re-cite.

On the addressing syntax: `[Doc:dd, Table tt, Row rr, Col cc]` is already implemented in this exact domain — FinGround (arXiv:2604.23588, Apr 2026) uses it with structure-aware chunking that carries header metadata alongside each cell, and reports 92.1% citation precision on FinanceBench. But there's **no ablation isolating the cell-address choice** — it's an existence proof that the syntax is being built, not a measurement of what it buys. Don't cite it as validation of the accuracy gain.

### An equation

```json
{"evidence_class":"derived","asset_id":"eq-012","page":5,
 "polygon":[[...]],"crop":"assets/eq-012.png","crop_sha256":"...",
 "latex":"t_t = AR_{w,t}/(s_t/\\sqrt{N})",
 "latex_status":"model-transcribed-unverified",
 "extraction_method":"ocr","produced_by":"...",
 "normalized_char_start":44120,"normalized_char_end":44131}
```

The span points at an **inert placeholder** in `normalized.txt` (`[eq-012]`), not at glyph soup. This is the second requirement: **Pass 0 must excise detected formula regions from the text.** Leaving `Tt = ARw,t/(st/ViN)` in place creates verbatim-verifiable garbage — the same class of defect as the table row that verifies while being misread. An uncitable gap is recoverable; a confidently-wrong citation is not.

**Never run verbatim string comparison on a formula asset.** It produces confident false failures (33% of visually-perfect UniMERNet outputs differ textually) and confident false passes (a plausible-but-wrong LaTeX string). The citable artifact is the crop + its hash + the polygon; the LaTeX is a derived, lower-trust field. If you ever want a quality gate, render both and compare images (CDM-style), and know that CDM itself correlates with human judgment at only r=0.34.

Label the id scheme honestly: there is no standard for addressing an equation. W3C Web Annotation (Rec. 23 Feb 2017) gives you `TextPositionSelector`, `FragmentSelector`, `SvgSelector`, `RangeSelector` and `refinedBy` composition — model the *evidence record* on that selector union. RFC 7111's `#row=`/`#col=`/`#cell=` is the nearest prior art for cells but is Informational, unimplemented, and applies only to `text/csv`. So: a stable opaque id plus a stored crop, described as a local convention.

### A chart

```json
{"asset_id":"fig-003","page":8,"bbox":[...],
 "crop":"assets/fig-003.png","crop_sha256":"...",
 "caption":{"text":"Figure 1. Cumulative average residuals...",
            "char_start":52011,"char_end":52063,"evidence_class":"verbatim"},
 "axis_text":[{"text":"Loser Portfolio","char_start":...,"evidence_class":"verbatim"}],
 "description":{"text":"...","evidence_class":"derived",
                "produced_by":"model@version","generated_at":"..."},
 "extracted_series": null}
```

Three trust tiers in one asset. The crop, page, bbox and any caption/axis text that genuinely exists as characters are `verbatim`. A chart-type classification would be `structural`. A prose description is `derived` and structurally cannot be cited.

**Never expose a sub-figure address like `fig-003:series=loser,x=36`.** Block-level citation is where models measurably fail (44.66 precision vs 81.81 page-level), and asking a model for geometry directly hallucinates 82–97% of the time. Give the model a **closed set of asset ids** and resolve to geometry server-side.

**For a numeric claim about a chart, the correct move is not to read the chart.** Find the author's own tabulation of the same data elsewhere in the document and cite that span. This is usually available: SEC Reg S-K Item 201(e) performance graphs are conventionally accompanied by a table of the plotted cumulative-return values, and papers usually tabulate their figures. Where no tabulation exists, record **`value_not_verifiable_from_source`** rather than emitting a VLM reading. That's a real answer, and it's what the field's accessibility guidance (WCAG 1.1.1 / W3C WAI complex-images) has said for years: the underlying data comes from the author, not from pixels.

One gotcha to carry: Azure documents that figure and table bounding regions cover core content and **exclude caption and footnotes**. If you crop by bbox you lose the caption, which for a chart is often the only thing making it interpretable. Store the caption as a separate linked field.

## 4. BUILD ORDER

Effort in developer-days for someone who knows the codebase. "Proven" means the named test on your five real documents: GE Aerospace 10-K, De Bondt & Thaler 1985, Sharpe *Arithmetic of Active Management*, Andersen *Little Mermaid*, statement-classifier-spec.

### Step 0 — Stop the bleeding in the HTML path · **0.5 day**

Add `td|th|table|thead|tbody` to the closing-tag rewrite in `_normalize_html`, emitting a tab for cells and a newline for rows. Route HTML through Docling instead of the regex, or keep the regex as a fallback.

**Proven:** re-run GE; `"202520242023"` does not appear in `normalized.txt`, and no unit's evidence excerpt contains a digit run spanning a former cell boundary. Andersen, Sharpe and the spec doc produce byte-identical `normalized.txt` to today (no regression on the three clean sources).

*This is the cheapest fix in the list and it removes the worst artifact. Do it before anything else, on its own branch.*

### Step 1 — Bundle manifest + element index sidecar · **2–3 days**

Extend the Pass 0 manifest with `schema_version`, `offset_unit` (`"unicode_code_point"` for Python), parser name+version. Emit `elements.jsonl` beside `locator_map.jsonl`: every typed element with global char span, page, bbox where available, `extraction_method`, `produced_by`. No behavior change downstream yet.

**Proven:** for all five sources, every element's `[char_start, char_end)` slices out of `normalized.txt` byte-identically to the element's own stored text. Round-trip test in `tests/test_normalize_rich.py`. Existing `test_pipeline_integration.py` still green.

### Step 2 — Table assets with per-cell anchors · **4–6 days**

Grid extraction: DOM-native for HTML (exact, no ML), Docling/TableFormer for PDF. Store cells with index, spans, header flags, per-cell char span, `grid_sha256`. Write CSV alongside. Add `evidence_class` to the evidence record and the `structural` check to `audit.py`.

**Proven:** hand-label ~40 cells across the GE segment and income-statement tables. Report kip's own cell-index accuracy — expect the 0.67–0.86 regime, not 0.97 — and *require 100% label↔index self-consistency* on every stored citation. Then the specific regression: a claim citing "Total segment revenue, 2025" resolves to a cell whose char span slices to `$33,314`, and deliberately corrupting the stored header text makes `audit.py` fail the candidate.

### Step 3 — XBRL fact assets (GE only) · **3–4 days**

Arelle on the filed instance. Emit fact assets with full context including dimensional members. Add the value check: `transform(display_text, format, scale, sign) == fact.value`.

**Proven:** every number in the GE consolidated statements of income and the segment note resolves to an `ix:nonFraction` fact, or is explicitly recorded as untagged. Report the tagged fraction across all 107 tables honestly — it will be well under 100%. Then construct the adversarial case: find a fact where `@scale` or `@sign` makes displayed text differ from value, and show the value check catches what the verbatim check passes. **That single test is the proof that this step earned its keep.**

### Step 4 — Formula and figure assets on the scanned PDF · **3–5 days**

Two-stage: layout detection (Docling Heron) → tight crop → recognition on the crop. Never hand a page region to a formula model. Write the crop unconditionally, even when recognition fails. Excise formula regions from `normalized.txt`, replacing with inert placeholders.

**Proven:** on De Bondt & Thaler — every detected formula region has a crop file that opens and a non-degenerate polygon; the string `"ViN"` no longer appears in `normalized.txt`; no evidence record's char span overlaps a formula or figure region; and the chart's axis-tick noise (`"0.20- 0. 15-]"`) is gone from citable text, replaced by `fig-NNN` with a crop. Missing-crop → pipeline error, tested.

### Step 5 — Trust-tier enforcement · **1–2 days**

`evidence_class` mandatory on every evidence record. `audit.py` rejects any candidate whose primary evidence is `derived`.

**Proven:** inject a synthetic figure asset with a fabricated `description`, build a candidate citing it as primary evidence, assert `audit.py` returns fail with a named reason. Assert the existing approved candidates across all five runs still pass.

### Step 6 — Five-document regression harness · **2 days, then ongoing**

Freeze the hand-labeled cells from Step 2 plus the formula/figure region counts from Step 4 as fixtures. Score cell-index accuracy and asset-recall on every parser upgrade.

**Proven:** bump Docling one minor version; the harness reports a diff rather than the pipeline silently changing what it cites.

**Total: roughly 15–22 days.** Steps 0 and 3 have the best ratio of accuracy gained to effort. Step 2 is the largest and the one where you should expect to discover your own numbers are worse than you hoped.

## 5. WHAT NOT TO DO

**Don't extract numbers from charts.** The best system on the leading benchmark scores 60.1 (Docling's own Chart2CSV number, on their own blog, for their own model). Specialist chart models collapse out-of-domain — TinyChart 95.2 → 28.6, DePlot last at 23.06. Missing cells run 22–42%, so an extracted table looks complete while omitting a series. "Just run DePlot on it" is a 2023 plan that is now the worst evaluated option.

**Don't let a VLM figure description become evidence.** GPT-5 scores 34.46% on ChartHal, with failures concentrated precisely on content absent from the chart. Store the description if it helps a human; type it `derived` and bar it structurally.

**Don't ask a model to emit coordinates or bounding boxes.** 82–97% attribution hallucination across six open VLMs — models produce a correct answer pointing at the wrong region. Give a closed set of ids; resolve geometry server-side. (Caveat: that paper tested zero-shot prompting on mid-size open models, and its winning alternative was verbatim-quote matching, which is closer to what kip already does than to asset ids. The negative result is solid; read it as "don't emit geometry," not "asset ids are validated.")

**Don't build on TATR.** Hard architectural cap of `n_queries=125` per table — rows + columns + spanning cells beyond that are physically unrepresentable, and the failure is *silent row loss*. GE's 10-K has 1,573 `<tr>` across 107 tables; a single large statement can plausibly exceed it. (Correction to the common framing: TATR isn't deprecated and Aryn didn't replace it — they ship a hybrid, using TATR for small tables where it performs better. It's mature and capped, not dead.)

**Don't pick a parser from a vendor benchmark.** Unstructured's SCORE-Bench has Unstructured in the top three positions. Reducto tops RD-TableBench. LlamaIndex's May-2026 comparison concludes LlamaParse leads and publishes no dataset, no sample size, no scores. OmniDocBench is built by OpenDataLab, who build MinerU, which tops it. olmOCR-Bench is AI2's, and AI2's model was top when published. Pulse AI's April 2026 audit of a widely-used table benchmark found 4.3% of ground-truth files with verifiable errors and 89 files byte-identical to one vendor's own output. None of these are independent. Build your own five-document harness.

**Don't quote TEDS as if it measured your defect.** TEDS r=0.684 against human judgment of correct header association. The reference model's own scorecard says it: GriTS_Con 0.985 alongside whole-table exactness 0.824, same model, same test set.

**Don't verbatim-string-compare formulas.** ExpRate 0.4799 vs ExpRate@CDM 0.8110 on identical outputs. You will generate confident false failures on correct formulas and confident false passes on wrong ones.

**Don't turn on Docling's formula enrichment and trust the output.** It's off by default for a reason, the placeholder it leaves isn't addressable to a crop (Discussion #925, unanswered), there's an open LaTeX spacing bug (#2374), and Issue #1883 is literally titled "Formula extraction is tacky and inconsistent."

**Don't build a quality gate on a vendor's per-object confidence score.** Azure's formula confidence is documented as hard-coded. TATR's cell confidences are near-binary and uninformative on heterogeneous data. Compute your own signal.

**Don't emit markdown as the intermediate representation, for anything.** GFM tables cannot express rowspan/colspan at all, which is exactly how a spanning group header collapses into `SEGMENT REVENUE AND PROFIT202520242023`. Markdown is a disposable rendering for prompt context; the stored citation points at the grid.

**And don't pick a table serialization by asking "which format do LLMs read best."** The literature people cite for this doesn't say what it's claimed to say — the widely-quoted "Notation Matters" paper is actually about token-optimized formats for agentic tool schemas, not document tables, and the vendor blog behind the Markdown-beats-HTML number tested one small model on synthetic key-value records. Choose for addressability. That argument is structural and doesn't need a benchmark.

**One thing that is popular *and* right, so don't skip it:** cropped typed assets on disk, linked from a manifest JSON. Adobe has shipped it since October 2021. Azure, Docling, MinerU, Reducto, Chunkr and Marker all do variants. You're not inventing anything here, which is the best possible sign.

### Mathematical formula recognition — detection, recognition to LaTeX/MathML, benchmarks, and what production document pipelines actually do

#### `string-equality-is-not-verification` — Verbatim string comparison of a formula is close to meaningless as a correctness signal. The same formula has many equally-correct LaTeX spellings, so exact-match and edit-distance metrics fail badly. UniMERNet scores ExpRate (exact string match) 0.4799 but ExpRate@CDM (visually exact after rendering) 0.8110 on the same test set — i.e. ~33% of its outputs are visually perfect yet textually different from ground truth. A 2026 benchmark measured BLEU and Levenshtein at r ≈ 0 correlation with human judgment of formula correctness.
- **Evidence:** Wang et al., 'Image Over Text: Transforming Formula Recognition Evaluation with Character Detection Matching' (arXiv:2409.03643, CVPR 2025). UniMER-Test table: Pix2tex ExpRate 0.1237 / ExpRate@CDM 0.2910 / BLEU 0.4080 / CDM 0.6360; Texify 0.2288 / 0.4950 / 0.5890 / 0.7550; Mathpix 0.2610 / 0.5000 / 0.8067 / 0.9510; UniMERNet 0.4799 / 0.8110 / 0.8425 / 0.9680. On the SCE (screen-capture) subset the ranking REVERSES: BLEU says Mathpix (0.8182) beats UniMERNet (0.6160); CDM says UniMERNet (0.9671) beats Mathpix (0.9238). Rewriting 50 formulas five ways with GPT-4 left CDM constant at 1.0 while BLEU scattered. Human study: 1,008 samples, 64% preferred CDM, 32% called both equally credible (96% total agreement). Separately, Horn & Keuper, 'Benchmarking Document Parsers on Mathematical Formula Extraction from PDFs' (arXiv:2512.09874, v2 dated 2026-05-06): 250 formula pairs, 750 ratings, 30 human evaluators — Pearson r with human ratings was 0.78 for LLM-as-judge (GPT-5), 0.34 for CDM, and ≈0 for BLEU/Levenshtein.
- **Maturity:** research-sota · **Confidence:** high
- **Failure modes:** CDM itself is not a free lunch: it needs both sides to RENDER, so a syntactically broken LaTeX prediction cannot be scored; Horn & Keuper report CDM gives false positives on positional errors and false negatives when a model outputs Unicode instead of LaTeX, and measured its human correlation at only r=0.34. LLM-as-judge scored best (r=0.78) but costs an API call per formula and is itself unaudited.
- **Relevance to kip:** This is the direct analogue of kip's table defect, applied to formulas: a formula asset that passes verbatim string verification tells you nothing about whether the formula is right, and a formula that FAILS verbatim comparison is very likely still correct. If kip stores formulas as LaTeX assets, the verification step must render both candidate and reference and compare images (CDM-style), not compare strings. Practical design consequence: the formula asset should carry (a) the LaTeX, (b) the source crop image, and (c) a render-comparison verdict — because only (b)+(c) can adjudicate. Do not let Pass-N verbatim checks run on formula assets at all; they will produce confident false failures and, worse, confident false passes when a model emits a plausible-but-wrong string.
- **Narrowed by verifier:** Two narrowings. (1) The SCE-subset CDM for UniMERNet is 0.9461 in the arXiv v2 table, not 0.9671 as claimed; Mathpix 0.9238 and BLEU 0.8182/0.6160 are correct, so the ranking-reversal point holds unchanged, but the specific number is off. (2) The claim leans on CDM as the trustworthy metric while also citing Horn & Keuper's r=0.34 for CDM against humans. Those sit in tension: CDM is far better than BLEU but is itself only weakly correlated with human judgment, and Horn & Keuper found it false-negatives on Unicode output. The safe reading is 'string metrics are actively misleading', not 'CDM is a correctness oracle'. Also v2's date is 2026-05-05, not 2026-05-06.
- **Verifier checked:** Pulled the arXiv v2 HTML of 2409.03643 directly. Every headline number matches: Pix2tex 0.1237/0.2910/0.4080/0.6360, Texify 0.2288/0.4950/0.5890/0.7550, Mathpix 0.2610/0.5000/0.8067/0.9510, UniMERNet 0.4799/0.8110/0.8425/0.9680. GPT-4 rewrite experiment confirmed as 50 formulas x 5 rewrites = 250 variants, CDM constant at 1.0 while BLEU scattered. Human study confirmed: 1,008 predictions, 64% prefer CDM / 32% both good / 3% BLEU / 1% neither. Paper is real, CVPR 2025, Wang/Wu/Ouyang/Gu/Zhang/Xia/Zhang/He. Separately confirmed Horn & Keuper 2512.09874 (Pius Horn, Janis Keuper, v1 2025-12-10, v2 2026-05-05, accepted ICPR 2026): abstract states Pearson r=0.78 for their LLM-based assessment, 0.34 for character-level matching, ~0 for text similarity; 250 formula pairs, 30 evaluators, 750 ratings. Arithmetic 0.8110-0.4799=0.3311 checks out.

#### `recognizers-collapse-off-the-crop` — Specialized formula recognizers are trained on tightly-cropped single expressions and collapse when handed paragraph- or page-level regions. UniMERNet drops from 0.965 CDM on its own benchmark to 0.524 on page-level real-world formulas — a 46% relative collapse. Detection/cropping, not recognition, is where the accuracy actually goes.
- **Evidence:** Zhong et al., 'DocTron-Formula: Generalized Formula Recognition in Complex and Structured Scenarios' (arXiv:2508.00311v1, 2025-08-01). CSFormula benchmark built from 5,827,854 StackExchange pages (math/physics/chemistry), three structural levels — line-level (741,016 train / 1,000 test), paragraph-level (135,575 / 1,000), page-level (131,876 / 1,000). CDM results: DocTron-Formula 0.985 Im2LaTeX-160k / 0.961 UniMER avg / 0.873 CSFormula avg; UniMERNet 0.991 / 0.965 / 0.524; Mathpix 0.969 / 0.949 / 0.733; Qwen2.5-VL 0.971 / 0.911 / 0.622; GPT-4o 0.929 / 0.783 / 0.536. Note that UniMERNet is the BEST model on the cropped benchmarks and the WORST on page-level.
- **Maturity:** research-sota · **Confidence:** medium
- **Failure modes:** CSFormula is StackExchange-sourced, so it is web-typeset, not scanned print; the collapse on a 1985 photocopied two-column finance paper is plausibly worse than 0.524 and nobody has measured it. DocTron-Formula's own 0.873 is on its own training distribution — treat as an upper bound.
- **Relevance to kip:** Pass 0 cannot just hand a page region to a formula model. The bundle needs an explicit two-stage step: mathematical formula detection (MFD) producing a tight polygon per formula, then recognition (MFR) on that crop. The polygon must be stored on the asset — it is both the provenance anchor (page + bbox, parallel to kip's existing char-offset→page locator) and the thing that makes re-recognition with a better model possible later without re-running Pass 0. Also: benchmark numbers quoted for UniMERNet/Pix2Text in vendor comparisons are cropped-input numbers and will not be reproduced by kip on a 1985 two-column scan.
- **Narrowed by verifier:** The central number is mislabeled. 0.524 is UniMERNet's CSFormula AVERAGE across line+paragraph+page, not its page-level score. Its actual page-level CDM is 0.009 — essentially total failure, not a '46% relative collapse'. Line-level it holds at 0.919; paragraph 0.644; page 0.009. So the real shape is a cliff between paragraph and page, and the claim understates it by ~50x while attributing the wrong number to the wrong cell. Two further narrowings: CSFormula is rendered from StackExchange LaTeX posts, so 'page-level real-world formulas' overstates it — these are synthetic renders, not scans. And UniMERNet is architecturally a single-cropped-expression model, so page-level input is out-of-design use rather than a discovered weakness; the finding 'detection/cropping is where accuracy goes' is a reasonable design inference but is not what the paper measured.
- **Verifier checked:** Fetched arXiv 2508.00311v1 HTML. Paper is real (Zhong et al., Meituan, 2025-08-01). Every dataset figure verified: 5,827,854 StackExchange source pages, 741,016/135,575/131,876 train at line/paragraph/page, 1,000 test at each level. The CDM table verified exactly for all five models, including the Im2LaTeX and UniMER columns. UniMERNet is indeed best on Im2LaTeX-160k (0.991) and worst on CSFormula.

#### `azure-already-ships-the-bundle` — The bundle-with-addressable-assets design kip is considering is already the shipping production design at Microsoft. Azure AI Document Intelligence replaces each formula in the flat `content` string with a `:formula:` placeholder and emits a parallel `formulas` collection where each entry carries kind, LaTeX value, polygon, and a span back into the text. It has been GA since the 2023-07-31 API version.
- **Evidence:** Azure AI Document Intelligence add-on capabilities docs (page ms.date 2026-06-22, updated 2026-07-10), `ocr.formula` / `features=formulas` on `prebuilt-layout`. Schema per formula: `kind` ("inline"|"display"), `value` (LaTeX string, e.g. an escaped \\frac form), `polygon`, `span`, `confidence`. Formulas are appended at the end of each page in the result. Same pattern is used for barcodes (`:barcode:` + `barcodes` collection). Formula extraction is billed as an Add-On (not free), available in 2023-07-31 GA and 2024-11-30 GA, and is off unless requested. Docs carry an explicit warning: "The `confidence` score is hard-coded."
- **Maturity:** production-shipping · **Confidence:** high
- **Failure modes:** Azure emits formulas at the END of each page rather than interleaved, so naive consumers reading `content` top-to-bottom lose the reading-order position; the `span` is what recovers it. Formula extraction is off by default and costs extra, which is precisely why most pipelines that use Azure never turn it on and silently ship `:formula:` placeholders with no formula behind them.
- **Relevance to kip:** Strong validation that the direction is right, plus a ready-made schema to copy: placeholder-token-in-text + asset-with-span is a proven shape and it keeps character-offset citation working. Two specific lessons. (1) Copy the `span` field — the asset must point back into normalized.txt, so an evidence record can cite either the span or the asset id and the two stay reconcilable. (2) Azure's hard-coded confidence is a warning: do not build a quality gate on a vendor-reported per-formula confidence, because at least one major vendor's is a constant. kip should compute its own gate (render-and-compare) rather than trusting a number in the asset.
- **Narrowed by verifier:** The implication is stronger than the evidence. Azure ships the parallel-collection half of the design, not the stable-id half. The in-text placeholder is a fixed literal :formula: for every formula — it carries no unique identifier, so resolution depends entirely on span offsets, and the doc notes formulas initially appear at the end of each page rather than in reading order. Combined with the hard-coded confidence (no per-formula quality signal), this is closer to 'Microsoft validates the parallel-asset direction' than 'Microsoft already ships what kip is proposing'. Also: formulas are nested under pages[], not a single document-level collection.
- **Verifier checked:** Fetched the live Microsoft Learn page (ms.date 2026-06-22, updated_at 2026-07-10). Every element verified verbatim in the doc: ocr.formula extracts into a formulas collection; inside content, detected formulas are represented as :formula:; each entry carries kind (inline|display), LaTeX value, polygon, span, confidence; the sample JSON shows exactly that shape with an escaped \\frac example. Version-availability table confirms Formula extraction as Add-On, present in both 2023-07-31 (GA) and 2024-11-30 (GA), absent in 2022-08-31 and v2.1. Docling ships `do_formula_enrichment = False`; without it, every equation becomes the literal HTML comment `<!-- formula-not-decoded -->` in the Markdown/JSON output, and users report they cannot retrieve the corresponding image crop.

- **Maturity:** production-shipping · **Confidence:** high

#### `latex-primary-mathml-derived` — Store LaTeX as the primary representation and derive MathML for rendering/accessibility — not the reverse. Every recognizer in the field emits LaTeX; essentially none emit MathML. MathML's advantage is semantic/accessibility rendering, and that advantage is now real (cross-browser since 2023, screen readers 2025-2026) but it is a display target, not a capture target. The sobering number: arXiv, converting from PERFECT LaTeX source with no OCR involved at all, achieves only 75% error-free HTML+MathML against a 90% target.
- **Evidence:** arXiv accessibility paper 'Scaling Accessible Mathematics on arXiv: HTML Conversion and MathML 4' (arXiv:2605.16562, May 2026): LaTeXML-based HTML conversion has run on every new TeX/LaTeX submission since 2023; target 90% error-free, current 75%; roughly 6,000 user reports with about half resolved; initial MathML 4 'intent' annotations added for speech output; a Rust port of LaTeXML is in progress for cost. MathML Core reached cross-browser completeness when Igalia landed it in Chromium in 2023 (Chrome/Edge 109+, joining Firefox 4+ and Safari 10+). NVDA supports accessible math in Firefox from version 2025.1, JAWS from its 2026 releases. Presentation MathML is overwhelmingly what exists in the wild; Content MathML (the actually-semantic variety) is rare. On the pipeline side: Azure DI returns `value` as LaTeX; Docling extracts LaTeX and only renders MathML on HTML export; LlamaParse emits `$$...$$`; Mathpix's MMD is LaTeX-based; UniMERNet, Nougat, Pix2Text, texify/Surya, GOT-OCR2.0, MinerU, PP-FormulaNet all emit LaTeX.
- **Maturity:** production-shipping · **Confidence:** medium
- **Failure modes:** LaTeX has no canonical form — the same formula has unbounded valid spellings, which is what breaks string-based verification (see finding 1) and what makes de-duplication of formula assets hard. MathML round-trip is lossy in both directions. The 75%/90% arXiv figures come from arXiv's own report and are self-assessed, not independently audited.
- **Relevance to kip:** Decide LaTeX as the stored `value` on the formula asset; generate MathML lazily if kip ever needs to render or make entries screen-reader accessible. Do not attempt to store Content MathML — it would require semantic interpretation nobody in this pipeline can verify. The arXiv 75% figure is the number to internalize for expectation-setting: even a lossless source-to-source conversion of math is a quarter wrong, so a pixels-to-LaTeX conversion of a 1985 scan must be treated as a claim requiring evidence, never as ground truth. That argues for the formula asset being marked as derived/unverified by default, distinct from character-span evidence which is verbatim-verifiable.
- **Narrowed by verifier:** The 'sobering number' does not mean what the claim says. 75% is error-free HTML conversion overall, not MathML or math-specific accuracy — LaTeX macro and package handling, floats, bibliographies and layout all feed that 25%. #### `unicode-vs-latex-is-a-silent-corruption-channel` — The single most under-appreciated failure mode is representation mismatch: models frequently emit Unicode math characters (∑, √, ∂, ×) instead of LaTeX commands, and pipelines that flatten a formula into a text stream leave partially-rendered glyph soup that looks like text and verifies like text. This is exactly the mechanism that produced kip's 'Tt = ARw,t/(st/ViN)' artifact — the √ glyph was already rasterized/mapped to unrelated characters before any model saw it.
- **Evidence:** OmniDocBench changed its evaluation code in 2026 to add a hybrid matching algorithm allowing formulas and text to be matched against each other, explicitly because models outputting formulas as Unicode were being scored as errors (repo update log, v1.6 dated 2026/04/10, ~296 pages added). Horn & Keuper (arXiv:2512.09874) list "Unicode vs. LaTeX representation mismatch" and "missing formula delimiters in parser outputs" among their top failure modes, and note CDM produces false negatives specifically on Unicode output. Nougat's authors identify math-mode ambiguity — multiple LaTeX strings rendering identically — as an inherent scoring problem. Traditional text extractors are the worst offenders: GROBID scored last of 21 parsers (5.70/10) and pypdf/pymupdf4llm 6.67-7.69, precisely because they read the PDF text layer and emit whatever glyph codes the font mapping yields.
- **Maturity:** production-shipping · **Confidence:** medium
- **Failure modes:** I could not find a published measurement of how often text-layer extraction silently corrupts inline math in real scanned or born-digital PDFs — the OmniDocBench code change and the Horn & Keuper failure-mode list establish that it happens and matters enough to redesign a benchmark around, but the RATE is unmeasured. This is a widely-observed-but-unquantified claim, and kip's own five-document corpus is currently better evidence for its own rate than anything published.
- **Relevance to kip:** Two concrete requirements. (1) Pass 0 must EXCISE detected formula regions from normalized.txt and replace them with an inert placeholder — because leaving the extractor's glyph output in the text stream creates verbatim-verifiable garbage, which is the same class of defect as the table row that verifies while being misread. Deleting the corrupted text is safer than keeping it. (2) The formula asset needs a normalization step and a recorded notation convention before any comparison; a Unicode-∑ transcription and a \\sum transcription of the same formula must not be treated as different evidence. If kip cannot detect a formula region, it should still prefer marking the span low-confidence over letting it flow into citable text — an uncitable gap is recoverable, a confidently-wrong citation is not.
- **Narrowed by verifier:** The citation is misdated and mis-versioned. That hybrid matching algorithm landed in OmniDocBench v1.5 on 2025/09/25, not in 2026. The 2026/04/10 v1.6 update is a different change: Multi-Granularity Adaptive Matching (MGAM), 296 new pages, and a 3x CDM speedup. (There is also a v1.7 on 2026/04/30.) Separately, the claim bundles two distinct failure modes as one. A VLM choosing to emit the character U+221A instead of \\sqrt is a representation-mismatch problem. kip's 'Vi' artifact came from OCR of a rasterized glyph in a 1985 scan, where the radical was mapped to unrelated characters before any model saw it — a glyph/encoding problem, not a representation choice. No cited source measured the second. State the first as evidenced and the second as a plausible hypothesis about kip's own data.
- **Verifier checked:** The mechanism is real and independently confirmed. Horn & Keuper state that rule-based tools such as pypdf and pymupdf4llm output Unicode symbols exclusively, while vision parsers including dots.ocr and Nanonets-OCR-s do so frequently; they list missing formula delimiters as a systematic failure and note CDM cannot process non-LaTeX symbol formats, producing matching failures. ### Figure, chart and diagram understanding: region/caption extraction, chart-to-data, and the citability of a model-inferred chart reading

#### `chartqa-saturated-real-charts-collapse` — The benchmark everyone quotes (ChartQA) is saturated and no longer measures anything. On realistic charts, frontier VLMs lose 35-50 points, and crucially they cannot reliably tell when a chart does NOT contain the answer — abstention accuracy is near coin-flip.
- **Evidence:** ChartQAPro (arXiv:2504.05506, 7 Apr 2025; ACL Findings 2025): 1,341 charts from 157 sources, 1,948 questions incl. unanswerable/fact-check/conversational. Claude 3.5 Sonnet 90.50% on ChartQA -> 55.81% on ChartQAPro (best score, with CoT). GPT-4o 40.48%. Gemini 2.0 Flash 51.44%. Qwen2-VL-7B 89.5% -> 37.17%. Human baseline 85.02%. On UNANSWERABLE questions specifically: Gemini 2.0 Flash 63.14%, GPT-4o 50.13%, Claude 3.5 Sonnet 47.98%. Fact-checking: Claude 52.04% direct, 65.16% with CoT. Open-source models often get WORSE with CoT/PoT prompting.
- **Maturity:** research-sota · **Confidence:** high
- **Failure modes:** Confident answers to unanswerable chart questions (~50% failure). CoT raises closed-model scores but degrades open models. Benchmark-quoting: a vendor citing 'ChartQA 90%' is citing a saturated benchmark.
- **Relevance to kip:** Any figure asset whose content is produced by a VLM must be typed as inference, never as evidence. The unanswerable numbers are the sharp point: a model asked 'what is the 36-month CAR for the loser portfolio in Figure 1' will answer ~50% of the time even when the chart cannot support the answer. kip's verbatim-verification gate cannot catch this, because there is no source string to compare against — this is the figure analogue of the table defect already found.

Also note the 35-50 point collapse is measured against ChartQA specifically; ChartQAPro changes question TYPES (unanswerable, conversational, hypothetical, fact-check) as well as chart realism, so the drop conflates harder charts with harder question formats. For kip that is arguably better, not worse, evidence — but it is not a clean 'realistic charts' ablation.

#### `chart-to-table-numeric-reading-is-the-bottleneck` — Chart-to-table extraction on realistic, data-label-free charts is far weaker than QA scores suggest. The bottleneck is precise numeric reading, not chart structure. The specialist models built for this task (DePlot, MatCha, TinyChart, UniChart) are effectively obsolete out-of-domain — TinyChart scores 95.2 on ChartQA and 28.6 on a realistic extraction set.
- **Evidence:** WB-ChartExtract (arXiv:2605.27298, 2026): 1,000 synthetic charts from World Bank series (52 indicators, 218 countries, 65 years), 4 chart types x 4 plotting libraries, ~7x more datapoints per chart than ChartQA. RMS_F1: Gemini 2.5 Pro 87.83; Claude Opus 4.6 60.99; Qwen3-VL 52.91; GPT-5.1 51.26; Seed 1.6 Flash 35.08; Llama 4 Scout 30.41; TinyChart 28.61 (vs 95.20 in-domain on ChartQA); DePlot 23.06. Error decomposition: Value Errors 19-40%, Missing cells 22-42% across models; area charts drop 12+ points vs bar charts. Separately, ExChart-Bench (arXiv:2606.29808, CHI 2026): 3,600 chart-table pairs, 33,757 numeric values, charts WITHOUT data labels — Adaptive MAPE: Gemini 2.5 Flash 6.72%, GPT-4.1 7.49%, Qwen2.5-VL-32B 10.70%, InternVL3.5-4B 11.75%, GPT-4o 13.38%, Qwen2.5-VL-7B 16.01%. Chart-specialist baselines on the same task: MatCha RMS 19.52, UniChart RMS 43.58. Targeted training (coordinate-perception + chart-table alignment, 90k synthetic samples) takes Qwen2.5-VL-7B from 16.01% to 4.87% MAPE.
- **Maturity:** research-sota · **Confidence:** high
- **Failure modes:** In-domain specialist models collapse out-of-domain (TinyChart 95.2 -> 28.6). Missing rows/series are as common as wrong values, so an extracted table can look complete and silently omit a series. Dense charts (>~30 points) degrade sharply.

#### `chart-descriptions-hallucinate-too` — Falling back to 'just have a VLM describe the figure in prose' does not dodge the problem. Dense chart captioning hallucinates at measurable rates, and the trigger case is information absent from or contradicting the chart — the same case a citation pipeline most needs to get right.
- **Evidence:** ChartHal (arXiv:2509.17481, Sept 2025): fine-grained hallucination taxonomy for chart understanding, 1,062 human-validated samples. Reported accuracies include GPT-5 34.46% and o4-mini 22.79%. Headline finding: questions involving information absent from, or contradictory to, the chart are especially likely to trigger hallucination. ChartCap (arXiv:2508.03164, Aug 2025) attacks the same problem for dense chart captioning and introduces a dedicated hallucination-aware metric, evaluating frontier models including Claude 3.5. Complementary: SciFIBench (NeurIPS 2024 D&B, arXiv:2405.08807) — 2,000 questions, adversarially-filtered hard negatives, figure->caption and caption->figure matching over SciCap arXiv figures; 28 LMMs evaluated; GPT-4o and Gemini 1.5 best and beat some individual humans, but mean human score still beats every model.
- **Maturity:** research-sota · **Confidence:** medium
- **Failure modes:** Descriptions assert trends, comparisons and values not present in the figure. Frontier reasoning models score under 35% on the hallucination benchmark. Even figure<->caption matching, a far easier task than value reading, is below human mean.
- **Relevance to kip:** A generated figure description is a claim about the source, not source text — and it is a claim that fails hardest exactly where the pipeline is exposed (content not actually in the figure). On 10-K-style pages, human annotators themselves only agree on caption boxes 40-61% of the time.
- **Evidence:** PDFFigures 2.0 (Clark & Divvala, JCDL 2016 — note: 10 years old, still the standard baseline): 94% precision at 90% recall on CS papers; caption association is regex on 'Figure N' plus Hungarian assignment minimizing Euclidean distance between box centers. DocLayNet (Pfitzmann et al., KDD 2022, arXiv:2206.01062), inter-annotator agreement measured as pairwise mAP@0.5:0.95 on triple-annotated pages — Caption class: 84-89% all documents, but 40-61% Finance, 94-99% Science, 95-99% Law; Picture class: 69-71% all documents, 56-59% Finance, 82-86% Manuals. Current SOTA open layout models: Docling's Heron family ('Advanced Layout Analysis Models for Docling', arXiv:2509.11720, Sept 2025) — RT-DETR/RT-DETRv2/D-FINE detectors trained on ~150,000 documents, 20.6-23.9% mAP improvement over Docling's prior baseline at comparable runtime; heron-101 reaches 0.758 mAP on DocLayNet-v2; heron became Docling's default layout model around Dec 2025.
- **Maturity:** production-shipping · **Confidence:** high
- **Failure modes:** Caption regex assumes 'Figure N' numbering — financial filings frequently have untitled, unnumbered graphics with only a heading above. Distance-based matching mispairs when two figures share a page. Layout models trained on paper-like pages generalize poorly to dashboards and infographics. #### `no-standard-for-citing-a-chart-cite-the-region-not-the-reading` — There is no accepted standard for citing a chart's CONTENT as source text, and nobody has one. The emerging practice — in both multimodal-RAG research and accessibility guidance — is to cite the region (page + bounding box, or a cropped image), and to treat any numeric reading as either author-supplied data found elsewhere in the document, or as inference that is displayed separately from the citation.
- **Evidence:** FinRAGBench-V (arXiv:2505.17471, 23 May 2025; EMNLP 2025 Main, aclanthology 2025.emnlp-main.211) is the first systematic evaluation of visual citation: bilingual corpus of 60,780 Chinese + 51,219 English pages, 855 + 539 human-annotated QA pairs, with an automatic citation-evaluation method scoring precision and recall at BOTH page level and block level, using box-bounding and image-cropping as the two citation-rendering strategies; the baseline system RGenCite integrates visual citation into generation. Headline: MLLMs cite competently at page level and struggle at block level. GranuRAG / GranuVistaVQA (arXiv:2605.15019, May 2026) makes the same argument — coarse image-level retrieval makes failures unverifiable — and promotes visual elements to first-class retrieval units with attribution-constrained generation, +29.2% over six baselines. Accessibility practice (WCAG 2.x SC 1.1.1) is the closest thing to a settled norm and is explicit that a chart needs short alt text PLUS a long description PLUS, where possible, the underlying data as an author-published table adjacent to the chart — i.e. the data must come from the author, not be recovered from pixels. Domain escape hatch relevant to kip: SEC Reg S-K Item 201(e) stock-performance graphs are conventionally accompanied in filings by a table of the plotted cumulative-return values, so the citable numbers usually exist as text elsewhere in the same document.
- **Maturity:** research-sota · **Confidence:** medium
- **Failure modes:** Page-level citation looks good in eval and is nearly useless for verification on a dense 10-K page. Block-level citation, the useful granularity, is where models measurably fail. There is no metadata standard (no MathML/LaTeX analogue) for chart data — SVG title/desc and HTML figcaption are the only in-band carriers, and none of kip's five sources uses them for data.
- **Relevance to kip:** Direct answer to kip's hardest question. A chart asset should be citable as an identity + locator (asset id, page, bbox, image hash) — that is verifiable and is what the field does. It should NOT be citable as text. If a numeric claim about a chart is needed, the correct move is not to read the chart: it is to find the author's own tabulation of the same data elsewhere in the source (very often present in 10-Ks and in papers) and cite THAT span. Where no such tabulation exists, the pipeline should record 'value not verifiable from source' rather than emit a VLM reading. Block-level citation being the measured weak point also argues against fine-grained sub-figure citation ids like 'fig-003:series=loser,x=36' — the field cannot yet verify those.
- **Narrowed by verifier:** Four narrowings. (1) GranuRAG's real title is 'From Scenes to Elements: Multi-Granularity Evidence Retrieval for Verifiable Multimodal RAG' (arXiv:2605.15019, 14 May 2026); the gain is 'up to 29.2% over six strong baselines', not a flat +29.2%; and it targets scenes/natural images broadly, so its transfer to document charts is an assumption, not a measured result. (4) Citation error: the claim sources Item 201(e) to SEC release 34-95607, which is the 2022 Pay Versus Performance adopting release — a different rule. Cite the SEC Regulation S-K compliance and disclosure interpretations instead. The core assertion — no accepted standard exists for citing a chart's CONTENT, and the emerging practice is to cite the region while treating any numeric reading as inference or as author-supplied data found elsewhere — holds.

#### `char-spans-and-typed-elements-coexist` — kip's framing of 'cites either a character span OR an asset id' is a false choice. The two largest cloud document-AI services keep a single global text string as the canonical citation surface AND layer typed elements on top of it, where every element — including every table cell and figure — carries an (offset, length) span into that string. This is the dominant production pattern for exactly kip's problem.
- **Evidence:** Azure AI Document Intelligence v4.0 (2024-11-30 GA): the top-level `content` property is a concatenation of all content elements in reading order, and 'all elements specify their position in the reader order via spans within this content string'. Spans are {offset, length}; by default in user-perceived characters (grapheme clusters), configurable to Unicode code points or UTF-16 code units via the `stringIndexType` query parameter. Tables, table cells, figures, formulas, styles and languages all carry spans; figures additionally carry `boundingRegions`, `elements` (JSON-pointer refs like "/paragraphs/15") and `caption`. Google Document AI: document.text is documented as 'the source of truth of the document's text'; every element carries layout.textAnchor.textSegments[] with startIndex/endIndex as UTF-8 char indices into that string, plus boundingPoly with vertices and normalizedVertices — and this applies down to individual table cells (Document.Page.Table.TableCell.layout). #### `cell-address-is-index-pair-not-header-text` — Every production system addresses a table cell by numeric (rowIndex, columnIndex) plus (rowSpan, columnSpan) and a header-role flag — never by header text. kip's proposed "tbl-004:row=Total revenue,col=FY2025" makes the address depend on the very thing the model got wrong (its reading of the headers), so a misread table would still produce a self-consistent, passing citation.
- **Evidence:** Azure DI cells carry rowIndex/columnIndex/rowSpan/columnSpan plus a `kind` enum: content, rowHeader, columnHeader, stubHead, description — and tables separately carry caption and footnotes, which are excluded from the table's own boundingRegion. AWS Textract CELL blocks carry RowIndex/ColumnIndex (1-based)/RowSpan/ColumnSpan, with MERGED_CELL blocks and TABLE_TITLE/TABLE_FOOTER relationships. Google Document AI splits tables into headerRows and bodyRows, each cell with rowSpan/colSpan and its own layout/textAnchor. Docling's TableItem holds TableData of TableCell objects with start/end row and column offsets and a column_header flag, generated by TableFormer, which explicitly handles 'partial or no borderlines, empty cells, rows or columns, cell spans and hierarchy both on column-heading or row-heading level'. Docling's internal table-structure token language is OTSL (Optimized Table Tokenization for Table Structure Recognition, 2023): it cuts the structure vocabulary to 5 tokens versus HTML's 28+, roughly halves sequence length, and is reported at ~93.6% accuracy on complex tables.
- **Maturity:** production-shipping · **Confidence:** medium
- **Failure modes:** Index-based addressing is only stable if the grid is stable. Re-running a different parser version can shift row/col indices (Docling issue #3698 reports multi-level headers shifting a row on merged headers). Mitigate by pinning the parser version in the bundle manifest and storing a content hash of the grid, so a re-parse that changes indices is detected rather than silently re-cited.

A citation like 'tbl-004:r7c3' is then verifiable against stored data; 'row=Total revenue,col=FY2025' is only verifiable against the model's own prose. #### `markdown-as-ir-is-the-documented-universal-failure` — Markdown (and any flat text serialization) is the most-documented failure mode in the field, and it is precisely the defect kip has. Markdown tables cannot express rowspan/colspan at all, so a spanning group header collapses and the grid misaligns — exactly the "SEGMENT REVENUE AND PROFIT202520242023" defect. Separately, the literature on which serialization LLMs read best is contradictory, so format should be chosen for addressability, not comprehension.
- **Evidence:** Documented losses in markdown conversion: bounding boxes and coordinates disappear entirely; reading order, confidence scores and complex table structure are lost. olmOCR (AI2) is the clean example — it emits per-page markdown/plain text for LLM training corpora and carries no bbox provenance; olmOCR 2 (arXiv 2510.19817, Oct 2025) scores 82.4 on olmOCR-Bench versus Marker 76.1 and MinerU 75.8, built on Qwen2.5-VL-7B and trained on olmOCR-mix-1025 (270,000 pages); olmOCR-Bench is 1,403 PDFs / 7,010 pass-fail unit tests covering text presence, reading order, tables, formulas and baseline behavior — a good linearization benchmark that says nothing about element provenance. Docling issue #3698 reports simple colspan/rowspan recovered but complex and irregular merges still open, with multi-level headers shifting a row. On serialization-vs-comprehension the sources actively disagree: an ImprovingAgents vendor test (Oct 2025) reports Markdown-KV at 60.7% accuracy versus HTML 53.6%, with CSV ~16 points below Markdown-KV; a 2025 tabular-understanding survey (arXiv 2508.00217) argues JSON edges out LaTeX and Markdown for TableQA because repeating the column name in every row removes the need to cross-reference headers; and 'Notation Matters' (arXiv 2605.29676) runs 9,649 prompt-completion trials across 11 models and 4 formats and finds format does not significantly affect aggregate accuracy, only per-model sensitivity.
- **Maturity:** production-shipping · **Confidence:** medium
- **Failure modes:** The markdown-loses-provenance claim is well documented but I found no controlled study quantifying downstream citation error caused by it — the causal link from 'markdown IR' to 'wrong cited number' is argued, not measured. kip's own five-document measurement is, as far as I can tell, better evidence on this specific link than anything published.
- **Relevance to kip:** Two consequences. First, do not pick a table serialization by asking 'which format do LLMs read best' — the evidence does not support a strong answer and the effect size is contested. Pick the one that is addressable and lossless: a cell-indexed grid, with HTML or OTSL as the serialization since both can express spans, and markdown only as a disposable rendering for prompt context. Second, whatever you serialize into the prompt, the stored citation must point at the grid, not at the serialization — otherwise you have reintroduced the defect one layer up.
- **Narrowed by verifier:** Three fixes. (1) MinerU's olmOCR-Bench score is 75.2±1.1 for MinerU 2.5.4, not 75.8. #### `xbrl-not-document-ai-for-the-10k` — For the GE Aerospace 10-K the correct move is not a better parser — the 2,863 ix:nonFraction facts bound to 701 xbrli:contexts are already an exact, machine-readable fact table with period and entity attached. And there is measured evidence that LLM reconstruction of those same facts is poor, which makes XBRL the authority and the model's table reading the thing being checked.
- **Evidence:** FinTagging (arXiv 2505.20650, May 2025) benchmarks exactly this on 30 SEC 10-K filings from 2024 — 76,835 narrative sentences (~16M chars) and 5,450 financial tables, with 3,354 sentences and 3,245 table sequences annotated, yielding 52,740 numerical entities across 2,288 unique US-GAAP concepts. Split into FinNI (identify and type the numeric fact: monetary, percentage, shares, per-share, integer) and FinCL (link it to one of 17,388+ US-GAAP concepts). Ten LLMs tested zero-shot. Best results: DeepSeek-V3 FinNI F1 0.7238 (P 0.6329 / R 0.8452), GPT-4o FinNI F1 0.6022; FinCL accuracy DeepSeek-V3 0.1715, GPT-4o 0.1664, with all models below 0.11 on the harder variant; end-to-end macro/micro F1 DeepSeek-V3 0.0582/0.1132, GPT-4o 0.0508/0.0860. Tooling: Arelle is the open-source XBRL/iXBRL processor; its 'Save Loadable OIM' export converts a filing to xBRL-JSON/CSV (the XBRL Open Information Model), which XBRL International itself recommends as the LLM-friendly form; the Arelle iXBRL Viewer renders tagged facts interactively.
- **Maturity:** production-shipping · **Confidence:** high
- **Failure modes:** Coverage is partial and uneven: iXBRL tags the financial statements and selected disclosures, not MD&A prose, and segment-level or narrative numbers are frequently untagged (a 2026 working paper, arXiv 2605.23924, exists precisely because segment disclosures are incomplete and non-comparable). So XBRL gives a high-confidence authority for a subset of numbers and silence for the rest; the pipeline must treat 'no matching fact' as unverified, not as contradicted. And it only helps inline-XBRL sources — nothing for the other four documents.
- **Relevance to kip:** Add an XBRL fact asset type to the bundle, alongside table/figure/formula. For inline-XBRL sources, Pass 0 should run Arelle and emit each fact as {fact_id, concept, value, unit, context(period, entity), decimals, char span in normalized.txt where the tagged value appears}. #### `ixbrl-facts-are-dom-anchored-so-cell-level-citation-is-already-in-the-file` — In inline XBRL, the `ix:nonFraction` element wraps the very text node that renders inside the HTML table cell. #### `ixbrl-displayed-text-is-not-the-fact-value-verbatim-verification-is-insufficient` — iXBRL explicitly separates what is printed from what is meant. `@scale` is a power of ten the displayed figure must be multiplied by; `@sign="-"` flips the sign independently of whether the printed text has parentheses; `@format` applies a Transformation Rules Registry rule to normalize the numeral. So a cell printing "33,314" can legitimately carry the value 33,314,000,000 and a cell printing "1,205" can carry −1,205. Separately, `@decimals`/`@precision` are routinely confused with scale, and XBRL International itself documents that this confusion plus "in thousands" units causes interoperability failures. A verbatim check against the printed string will pass on every one of these while the extracted number is wrong by three orders of magnitude or by sign.
- **Evidence:** XBRL International guidance, "iXBRL Tagging Features" (published 3 Oct 2019, still current guidance): scale = power of ten to reach the actual XBRL value (worked example: displayed 100 with scale=6 → 100,000,000); sign controls positivity independent of display parentheses; format applies TRR rules; decimals is a separate accuracy mechanism. XBRL International Working Group Note "Precision, Decimals and Units 1.0" (11 Jan 2017): precision/decimals are widely misunderstood as scaling/presentation; non-conformant implementations and 'thousands' units compound interoperability problems. XBRL US DQC rules address the same class in practice — e.g. DQC_0091 invalid percentage item values, where filers report percentages on a 0–100 scale instead of 0–1 and attach USD units to percentItemType elements.
- **Maturity:** production-shipping · **Confidence:** high
- **Failure modes:** Even correctly applied, scale/sign resolution depends on the filer having tagged correctly. DQC's existence is evidence that filers get sign and scale wrong at nontrivial rates. So the normalized value is more trustworthy than the flat string but is not ground truth — it is a filer assertion, and should be labelled as one.
- **Relevance to kip:** This is a defect in kip's verification model, not just its extraction model, and it is the same shape as the table defect already found. If evidence cites an asset, the asset must store BOTH the rendered text (for the human/verbatim check) and the normalized value with its scale, sign, decimals, and unit — and verification must check the value, not only the string. Concretely: for a numeric asset, verbatim-verify the display text AND assert the stored value equals transform(display_text, format, scale, sign). A citation that only pins the string is exactly as unsafe as today's flat table string, just harder to notice.
- **Narrowed by verifier:** Two small fixes. The worked example on the xbrl.org page is "$12.34 million" with scale 6 giving 12,340,000, not "displayed 100 with scale=6 -> 100,000,000" — use the real one. And I could not load xbrl.us/data-rule/dqc_0091 (timeout), so the specific percentage-scale/USD-on-percentItemType detail is unverified; the DQC rule family and the error class are real, but cite the XBRL International guidance rather than DQC_0091 as the load-bearing source.
- **Verifier checked:** xbrl.org "iXBRL Tagging Features", published 3 Oct 2019, confirms every mechanism: scale is a power-of-ten multiplier applied to the displayed figure; sign controls polarity in the XBRL output independently of display (values transform to positive unless sign is specified); format applies Transformation Rules Registry rules (num-dot-decimal, date-monthname-day-year-en etc.); and it explicitly states the scale factor is separate from the accuracy mechanism expressed via decimals or precision. The Inline XBRL 1.1 spec corroborates the scale attribute as an exponent of ten. The claim's core logical point — a verbatim check against the printed string passes while the extracted value differs by orders of magnitude or by sign — follows directly and is the single most decision-relevant finding in the set for kip.

### Provenance and citation for non-text content (tables, formulas, figures) in document-QA and RAG pipelines

#### `coordinate-attribution-hallucination` — Asking a model to cite non-text evidence by coordinates/bounding box is the single worst-performing attribution interface measured to date: models produce a correct answer while pointing at the wrong region 82–97% of the time. Replacing coordinates with a verbatim-quote interface, then matching the quote to a layout block, roughly quintuples evidence recall. This argues that kip's asset-id design should expose discrete symbolic handles the model selects, never raw geometry the model must emit.
- **Evidence:** "Evidence Attribution in Visual Document Understanding without Coordinates or Region Labels" (arXiv:2607.24651v1, 27 Jul 2026). Names the failure "attribution hallucination." Coordinate interface: max evidence recall 8.1%, hallucination rate 82–97% across six open VLMs. Language (verbatim-quote) interface + layout parser + multimodal retriever with Hungarian matching: 25.9–46.9% recall, hallucination 39–65%. After GRPO training on an 8B backbone: 51.3% recall, 33.8% strict attributed accuracy. Benchmarks: CiteVQA single-doc subset (719 verified bilingual questions over 440 PDFs), LongDocURL (1,584 training questions, 30-page windows); mean doc length 34 pages, max 182.
- **Maturity:** research-sota · **Confidence:** medium
- **Relevance to kip:** Strong evidence for the bundle direction, with one refinement: the model must never be asked to produce a bbox. Give it a closed set of asset ids (tbl-004, eq-012) and let the id resolve to geometry server-side. Note that even the best language-interface number is ~51% recall — asset-level attribution is inherently error-prone, so an asset citation needs its own verification step (does the cited asset actually contain the claimed value?), not just an existence check on the id.
- **Narrowed by verifier:** (1) 'Single worst-performing attribution interface measured to date' is not supported — the paper compares two interfaces on its own two benchmarks with six mid-size open VLMs; it is not a field-wide survey, and the coordinate condition is zero-shot prompting, not a grounding-tuned model. (2) 'Roughly quintuples' takes the top of the range; the paper's own framing is '+26–47 points', i.e. ~3.2x–5.8x off the best coordinate baseline. (3) Most important: the paper's winning interface is a verbatim quote that a retriever then matches to a layout block — it never tests a discrete symbolic asset-id interface. So the evidence argues against models emitting geometry; it does not argue for asset ids, and the design it validates is closer to kip's existing char-span/quote model than to the bundle. #### `standards-exist-for-cells-and-regions-none-for-equations` — There are stable, decade-old standards for addressing a text span, an image region, and a table cell — and effectively none for addressing an equation inside a document. RFC 5147 (Apr 2008) does `#char=`/`#line=` for text/plain. Media Fragments URI 1.0 supplies `#xywh=`. IIIF Presentation API 3.0 dropped the Open Annotation model in favor of the W3C Web Annotation model for image-region annotation. Community practice guidance (2025) is to prefer Media Fragment URIs / FragmentSelector for breadth of viewer support and reserve SvgSelector for genuinely non-rectangular regions. For math: the literature is about formula *retrieval* (MathML tree similarity, PHOC spatial regions, SSEmb 2508.04162, ARQMath-lineage work), not formula *citation* — no addressing standard surfaced in search.
- **Maturity:** production-shipping · **Confidence:** medium

(1) Model the asset id on RFC 7111's row/col/cell vocabulary rather than inventing one — `tbl-004#cell=3,7` with a header-name alias is closer to prior art than `row=Total revenue,col=FY2025`, and both can coexist. ### Table extraction and structure recognition — detection, cell structure, and row/column header association

#### `header-association-invisible-to-standard-metrics` — The field's two default metrics (TEDS and GriTS) do not isolate header-to-cell association, and both correlate only moderately with human judgment of whether a table was read correctly. A parser can flip a sign or drop a decimal and barely move TEDS, while a semantically identical re-serialization (thead vs tbody, th vs td) is penalized heavily. This is the exact blind spot the kip pipeline already has, reproduced at the level of the whole research field's evaluation apparatus.
- **Evidence:** "Beyond String Matching: Semantic Evaluation of PDF Table Extraction" (arXiv 2603.18652, 19 Mar 2026) ran 21 parsers over 451 tables on 100 synthetic pages with LaTeX ground truth, plus a human study of 1,554 ratings over 518 table pairs (Krippendorff alpha 0.77, human ceiling r=0.89). Correlation with human judgment: TEDS r=0.684, GriTS-Avg r=0.698, SCORE-Avg r=0.637; LLM-as-judge reached r=0.927 (Gemini-3-Flash-Preview) and r=0.939 (Claude Opus 4.6). The paper's stated criterion is whether "every cell value can be unambiguously mapped to its row and column headers," and on manual inspection even top systems showed misaligned spanning cells, subtly altered values, and incorrect header-cell associations. It documents a case where a parser turned 1.12 into 112 with negligible edit-distance cost. Pulse AI's benchmark survey (3 Apr 2026) makes the same structural criticism: TEDS treats a 2D table as a sequence and so lacks directional awareness — a column transposition and a content typo are penalized similarly.
- **Maturity:** research-sota · **Confidence:** high
- **Failure modes:** The 2603.18652 result rests on synthetic LaTeX-derived pages, not scanned real-world documents, so absolute parser scores are optimistic. Its recommended replacement (LLM-as-judge) is itself an LLM and inherits LLM failure modes — using it to certify a citation pipeline would be circular for kip's purposes.
- **Relevance to kip:** Two consequences. (1) If you adopt any off-the-shelf table model, its published TEDS number tells you almost nothing about the defect you care about — you must build your own header-association check. (2) The proposed asset design is the fix at the representation layer: citing 'tbl-004:row=Total revenue,col=FY2025' makes header association a stored, checkable fact rather than something reconstructed in prose. That is precisely what TEDS cannot see and what the field is only now building metrics for.
- **Narrowed by verifier:** Two narrowings. (1) The corpus is 100 SYNTHETIC pages generated from LaTeX ground truth, not real-world PDFs — the correlation figures are measured on clean generated documents, so they are a lower bound on how badly the metrics fail on scanned or degraded sources, but they are not evidence about real documents. (2) The specific sub-assertion that 'a semantically identical re-serialization (thead vs tbody, th vs td) is penalized heavily' does not appear in what I read of this paper; it is a known property of TEDS from elsewhere but is not sourced here — drop it or source it separately. #### `addressable-cell-with-row-col-index-is-the-shipped-industry-contract` — The 'cite a cell by table id plus row/column' design is not novel — it is what every major production document API already returns, and has for years. AWS Textract and Azure Document Intelligence both emit per-cell row/column indices, spans, geometry, and a first-class column-header flag. Docling's document model does the same with page provenance. The notable gap: all of them model column headers as a type but none gives a canonical row-header/stub designation, which is the half of the problem kip most needs.
- **Evidence:** Amazon Textract AnalyzeDocument with the TABLES feature returns CELL blocks with RowIndex, ColumnIndex, RowSpan, ColumnSpan, Geometry, Id, Relationships and Confidence, plus EntityTypes drawn from COLUMN_HEADER, TABLE_TITLE, TABLE_FOOTER, TABLE_SECTION_TITLE and TABLE_SUMMARY (indices are 1-based). Azure AI Document Intelligence prebuilt-layout returns table cells with rowIndex, columnIndex, rowSpan, columnSpan, content, boundingRegions, spans into the flat content string, and a kind field that takes 'columnHeader'. Docling (IBM/DS4SD, technical report arXiv 2408.09869; v2.72.0 released 3 Feb 2026) produces a DoclingDocument where every element is a typed node (section_header, list_item, table) carrying hierarchy level and page provenance, with TableFormer determining which cells belong to column headers, row headers, or the body, and handling partial/absent borderlines, empty cells, spans, and hierarchy. Docling and granite-docling additionally serialize tables in OTSL (Lysak et al., 2023), a token language designed to make table structure cheap to generate and validate.
- **Maturity:** production-shipping · **Confidence:** high
- **Failure modes:** Cloud API cell indices are a flat grid; deeply hierarchical or transposed financial tables get flattened into an index space that loses parent/child heading semantics, which reintroduces exactly kip's defect one layer down. Confidence scores on cells are per-cell OCR confidence, not confidence that the cell landed in the right slot — the two are routinely confused. And a 2013-era but still-standard normalization step (expanding rowspan/colspan into duplicate cells) is lossy in the other direction: it makes a spanning header indistinguishable from repeated identical headers unless you retain the original span.
- **Relevance to kip:** Direct validation of the proposed bundle: an asset id plus (row, col) address, with the header cells typed, is the format the ecosystem already speaks — so kip can consume Textract/Azure/Docling output into its asset schema with a thin adapter rather than inventing a representation. Two design notes fall out. First, keep the cell's byte span into the flat text (Azure's 'spans' field is exactly this), so an asset citation and a character-span citation are the same object viewed two ways and nothing downstream breaks. Second, since none of these APIs designates row headers canonically — Textract's TABLE_SECTION_TITLE is the closest approximation — kip must derive the row-label axis itself (the common heuristic is: walk left from a numeric cell until a non-numeric, non-date cell is found, accumulating nested labels), and should record that derivation as an assumption rather than a fact.

Azure AI Document Intelligence's DocumentTableCellKind enum has exactly five values: COLUMN_HEADER, CONTENT, DESCRIPTION, ROW_HEADER, and STUB_HEAD. It gives a canonical row-header designation AND a stub-head type for the corner cell — precisely the half of the problem the claim says nobody ships. The claim also refutes itself: its own Docling evidence says TableFormer decides whether cells belong to column headers, ROW headers, or the body (DoclingDocument's TableCell carries column_header, row_header and row_section flags). The accurate version is the narrower one: Azure and Docling both model row headers as first-class; AWS Textract is the outlier, with COLUMN_HEADER but no row-header or stub entity type. If kip wants row-header semantics off the shelf, Azure's layout model or Docling already provide it — that is a build-vs-adopt argument, not a gap to fill.
